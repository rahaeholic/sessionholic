# 터미널 화면이 예전 출력에 멈추는 문제

목표: 열린 터미널이 잠깐의 연결 실패나 iPad 복귀 뒤에도 최신 화면을 다시 받고, 읽기 재시도 소진 때문에 영구 정지하지 않게 한다.

확인: 운영 tmux 11개 중 copy-mode·종료 pane은 없고 출력 HTTP는 정상 200이었다. 이 조회만으로 사용자의 해당 기기 원인은 확정하지 않는다. 코드에서는 (1) AbortSignal.timeout 미지원 환경에 HTTP 기한이 전혀 없고, (2) 7번째 읽기 오류 뒤 자동 읽기가 끝나며, (3) 복귀·재연결도 이전 ANSI cursor부터 재생한다. 장시간 보관한 출력은 현재 화면으로 바로 복구하는 대신 과거 화면부터 처리할 수 있다.

가설과 재현: 미지원 timeout의 끝나지 않는 fetch, 재시도 소진 후 네트워크 정상화, 유효한 과거 cursor를 가진 복귀를 가짜 시계·전송으로 재현한다. 현재 구현에서는 기한·후속 읽기·fresh 요청 검증이 실패해야 한다. 확인되지 않은 native CLI 정지나 렌더러 결함은 원인으로 단정하지 않는다.

파일 매핑:
- 수정: `web/app.js` — HTTP timeout fallback, 출력 읽기의 짧은 기한, 소진 뒤 느린 자동 재연결, 복귀·오류 재연결의 fresh 화면, focus 시 중단된 읽기의 복구. 자동 복구가 입력 전달 결과 불명 잠금을 해제하거나 사용자 입력을 재전송하지 않게 한다.
- 수정: `tests/test_frontend.cjs` — 미지원 timeout과 caller 취소/정리, 끊긴 출력의 자동 재개, 숨김·종료·세션/인증 변경의 타이머 무효화, 이전 화면 즉시 재동기화, IME·초안·음성 객체 유지, 결과 불명 입력의 자동 재전송/잠금 해제 없음.
- 수정: `tests/test_session_control_frontend.cjs` — 독립 VM에도 실제 브라우저의 AbortController·AbortSignal을 제공해 전송 취소 기능을 포함한 기존 제어 검증을 유지한다.
- 수정: `docs/limitations.md`, `scripts/public-files.json` — 새 복구 정책과 계획 공개 목록.
- 참조만: `terminal.py`, `server.py`, `web/workspace.js`. 새 서버·수집기·연결 추정·사용자 세션 실행은 추가하지 않는다. 삭제 없음.

순서와 검증:
1. 위 세 조건을 기존 frontend fixture로 재현해 실패를 확인한다.
2. 읽기 전용 복구를 구현하고 해당 테스트 및 전체 JS 테스트를 통과시킨다. 공개 파일 감사와 diff 검사를 한다. 서버 코드 변경이 없으므로 Python 전체 검증을 반복하지 않고 기존 실제 tmux fresh 화면 fixture로 배포 환경의 화면 전달을 확인한다.
3. 최종 diff를 리뷰한 뒤 운영 최신 release를 보존해 한 번 배포한다. 별도 서버 canary·정적 해시·기존 터미널 ID·새 traceback·운영 제목 고정 보존을 검사한다. 사용자 대화에 시험 입력이나 종료는 보내지 않는다.

셀프 리뷰: 무제한 동시 요청 대신 하나의 읽기와 하나의 지연 복구만 유지한다. 새 화면은 tmux repaint로 받으며 원본 대화·history는 유지한다. 자동 복구로 초안/음성 DOM·포커스를 바꾸지 않는다. iPad의 공간을 넓히는 UI 설계는 이 출력 정지 수정과 별도이며 실제 하드웨어 검증 여부를 구분한다.
